# IMPLEMENTATION_PLAN: внутренняя платформа V2

Принципы: маленькие обратимые PR; публичный сайт не меняется; миграции и выкладка только с разрешения; ничего не отправляется клиентам, пока не подключён и не проверен канал и не оформлено согласие; одна база клиентов, записей, услуг, доступности и знаний.

## Блокеры и вопросы до PR3–PR7
1. Провайдер писем и адрес отправителя (домен). Без этого PR3 делается только в режиме dry-run.
2. Подтверждение Милой знаний и цен: сейчас знания помечены «DEMO placeholder».
3. Нужен ли отдельный вход Миле и сотрудникам (аккаунты, 2FA) до начала рассылок.
4. Согласие клиентов на сообщения: текст и реестр по каналам (юрист).
5. Хранилище для общего лимита запросов (D1/KV/Durable Object): выбрать, не вводя лишней сложности.
6. Политика хранения и удаления данных (сроки).

## PR1. Дашборд владельца (СДЕЛАНО в этой ветке)
Без новых таблиц и миграций. Плитки обзора стали ссылками на отфильтрованные списки; число на плитке и число строк считаются одним кодом (`src/lib/owner-queries.ts`); фильтры: сегодня, 7 дней, новые, ждут подтверждения, отмены; общий поиск; хронология клиента; лента действий; возврат с сохранением фильтра; постраничный вывод; телефон 320–430 px; axe без нарушений.
Приёмка: тесты `owner-queries.test.ts` (сверка счётчиков и списков, поиск, пагинация, изоляция салона), e2e `dashboard.cjs`.
Не вошло (осталось для следующих PR): метрики «follow-ups», «рефералы», «пробелы знаний», «возможности повторных визитов» (появятся вместе с данными в PR3–PR6, до этого не показываем выдуманных нулей).

## PR2. Календарь владельца
Дневной/недельный/месячный вид записей (по существующим данным), быстрые действия; правила перерыва и ограничения по услуге (дни, часы, максимум в день), буфер до записи, лист ожидания. Миграция 0005 (аддитивная): `service_rules`, `waitlist`. Больничный: превью затронутых записей без изменений; предложения клиентам только после PR3. Приёмка: тесты гонок, DST, буферов, освобождения слота; показ идентичной доступности на сайте, в ИИ и в кабинете.

## PR3. Основа жизненного цикла
Таблицы шаблонов, сценариев, задач; исполнитель по расписанию (Cron Triggers/Queue), идемпотентность, повторы, отмена при изменении записи; шаблоны RU/EN/UA; тихие часы; режим dry-run и симулированные часы; отправка выключена флагом, пока не подключён провайдер. Приёмка: сценарий «запись → подтверждение → напоминание → визит → follow-up» в песочнице, отписка соблюдается, отмена записи отменяет будущие задачи, ошибка доставки видна.

## PR4. ИИ-администратор
Типизированные серверные инструменты (слоты, бронь, перенос, отмена) с проверкой владельца записи; бронь только после явного подтверждения клиента; помощник владельца («я заболела») строит только превью. Приёмка: нет выдуманных слотов и цен, конфликт одновременных записей, эскалация при низкой уверенности.

## PR5. Центр знаний
Очередь пробелов, интервью «Обучи моего ИИ», исследование с источниками (черновик, не виден клиентам), состояния утверждения, оценочный набор вопросов EN/RU/UA. Приёмка по §6 ТЗ.

## PR6. Лояльность и рефералы
Журнал начислений (только добавление), коды и атрибуция, правила по услугам, защита от самореферала и повторов, выплата после состоявшегося оплаченного визита. Приёмка по §7 ТЗ.

## PR7. Кампании и соцсети
Только после проверки возможностей API платформ и согласий; сначала контракты адаптеров.

## Параллельно, без больших PR
Общий лимит запросов; отдельные входы и 2FA; экспорт и удаление данных клиента; резервная копия перед каждой миграцией (делает владелец в Cloudflare).
