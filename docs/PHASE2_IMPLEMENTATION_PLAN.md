# Этап 2. План без регрессий

Принцип: каждый шаг маленький, отдельный PR, до слияния проходит `npm run guard` (типы, 50 unit-тестов, вёрстка 144 страниц, запись, чат RU/EN/UA, сохранение чата) плюс новые тесты шага. Выкладка в production только после согласования владельцем. Миграции в production только с отдельным согласием.

## A. Сохранить без изменений

Серверное ядро записи (`booking.ts`, триггеры, идемпотентность, DST), календарь `/book` и `/manage`, сценарный движок и правила безопасности AI, передача мастеру, базу знаний с версиями и откатом, библиотеку и SEO-режим `noindex`, кабинет и CRM-основу, UTM первого касания, RU/EN/UA, печать ответа по словам, сохранение разговора, десктопный дизайн, `/concepts` (до решения), все 14 скрытых правил из реестра.

## B. Улучшить

Мобильный первый экран и логотип; нижняя панель на главной; ограничение частоты и определение IP; единый источник знаний AI; провайдерный адаптер и учёт стоимости LLM; кабинет библиотеки (чтение → редактирование); автоматическая проверка в CI.

## C. Добавить

AI-запись в диалоге (разбор даты/времени/услуги, hold, подтверждение кнопкой, перенос/отмена по ссылке); `conversation_id` и версия согласия; тест первого экрана; оценочный набор AI на 50–100 диалогов; редактор статей с согласованием Милой.

## D. Отложить

Лист ожидания, напоминания и aftercare (нужны почта и согласия), рефералы/бонусы (правил нет, проектировать с владельцем), аналитика воронки, SaaS-тарифы и мульти-салон (только документ), платежи, Instagram/WhatsApp, индексирование сайта.

## E. Требует уточнения

См. `PHASE2_OPEN_QUESTIONS.md` и конфликты К-1…К-5 в матрице.

## Карта зависимостей

```
PR-1 (hero, логотип, панель)       ── независим, без миграций
PR-2 (IP, лимиты, CI)              ── независим, без миграций; решение по правилам Cloudflare
PR-3 (AI-запись, часть А)          ── ядро не меняется; новый POST /holds; без миграций; К-2, К-3
PR-4 (AI-запись, часть Б)          ── МИГРАЦИЯ (conversation_id, версия согласия) ── после К-5
PR-5 (перенос/отмена в чате)       ── после PR-3
PR-6 (LLM: адаптер, один источник знаний, бюджет, оценка) ── К-4; зависит от PR-2 (лимиты)
PR-7 (редактор библиотеки)         ── МИГРАЦИЯ (статьи в БД) ── после К-5
PR-8 (CRM: лист ожидания и далее)  ── после почты/согласий; использует заготовки из feat/mk-knowledge
PR-9 (SaaS: проектный документ)    ── независим, без кода
```

## Порядок и объём

Рекомендую: PR-1 → PR-2 → PR-3 → (решение К-5) PR-4/PR-5 → PR-6 → PR-7; PR-8/PR-9 после. PR-1 можно показать владельцу первым (самая заметная и безопасная правка). До согласования ничего из этого не реализуется; на этом шаге добавлены только документы и статический прототип в `docs/phase2-assets`.

## Что можно без миграций и выкладки / что опасно

Без миграций: PR-1, PR-2, PR-3, PR-5, PR-6 (в основном), PR-9. Потенциально опасно: PR-4, PR-7, PR-8 (миграции боевой D1), а также любое изменение ограничителя частоты (можно заблокировать реальных клиентов), и перенос знаний AI в БД (меняет ответы).
